# База чатов фермы

Всё, что система знает про Telegram, лежит в одной SQLite-базе:
`~/.claude/skills/telegram/chats.db`.

Правило: **в Telegram ходим редко и по чуть-чуть, читаем — из базы.**
`get_dialogs` по всей ферме — это 15 секунд, флуд-вейт и лишний след активности;
`db_chats` — 0,1 секунды и никакого следа.

---

## 1. Что в базе

| Таблица | Что хранит |
|---------|-----------|
| `accounts` | за что отвечает каждый аккаунт фермы + суточные лимиты |
| `chats` | чат как таковой: id, тип, название, @юзернейм, описание, участники, свои метки |
| `chat_accounts` | что про чат знает конкретный аккаунт: состоит ли, непрочитанное, админ ли |
| `queue` | куда ещё предстоит зайти — по одному, с паузами |
| `actions` | журнал заходов; по нему считаются суточные лимиты |
| `messages` | кэш сообщений, чтобы читать историю не выходя в Telegram |

Чат хранится **один раз на всю ферму**, а «кто его видит» — отдельной таблицей.
Один и тот же чат, пришедший из синка диалогов `main` и из очереди `acc2`, — одна строка.

`id` чата всегда в «размеченном» виде, как отдаёт `get_dialogs`: канал `-100…`,
группа `-…`, человек — без знака. Приведение делает `peerId()` в `chatsync.cjs`
(`getEntity` отдаёт голый id — без приведения тот же чат лёг бы в базу дважды).

---

## 2. Наполнение

```bash
D=~/.claude/skills/telegram/driver.cjs

node $D db_sync                              # вся ферма: аккаунты + диалоги каждого
node $D db_sync '{"account":"main","limit":5000}'   # один аккаунт, глубже
```

`db_sync` делает один `getDialogs` на аккаунт (дёшево, но не чаще раза в сутки:
на 2000 диалогов Telegram уже вставляет 6-секундный флуд-вейт) и заодно подтягивает
ферму из `accounts.json`. Пауза между аккаунтами 3–8 с.

`limit` по умолчанию 500 — этого хватает на свежие диалоги. Полный проход
(`limit: 5000`) имеет смысл раз в неделю.

## 3. Чтение из базы (без Telegram)

```bash
node $D db_chats  '{"q":"фриланс","limit":20}'          # поиск по названию/@/описанию
node $D db_chats  '{"kind":"group","order":"size"}'     # группы по числу участников
node $D db_chats  '{"account":"acc2"}'                  # что видит конкретный аккаунт
node $D db_chats  '{"topic":"фриланс","tag":"активный"}' # по своим меткам
node $D db_chat   '{"username":"frilanserov_chat"}'     # карточка: аккаунты, очередь, кэш
node $D db_messages '{"chat_id":"@durov","limit":20}'   # кэш сообщений
node $D db_messages '{"q":"вакансия","limit":50}'       # поиск по всем сохранённым
node $D db_stats
```

`kind`: `user` · `bot` · `group` · `channel`.
`order`: `recent` (по умолчанию) · `size` · `title` · `seen`.

Свои метки — то, что превращает свалку в источник:

```bash
node $D db_tag '{"chat_id":"@frilanserov_chat","topic":"фриланс",
                 "tags":["blast-кандидат","активный"],"note":"26k, живой"}'
```

## 4. Кто за что отвечает

```bash
node $D db_accounts        # таблица ответственности + израсходованное за сегодня
node $D db_account_set '{"label":"acc2","role":"чтение",
   "duty":"радар, база источников, исполнитель очереди",
   "scope":["radar","sources","queue"],
   "join_limit_day":8,"read_limit_day":60,"msg_limit_day":0}'
```

| Поле | Смысл |
|------|-------|
| `role` | `личный` · `чтение` · `рассылки` · `резерв` |
| `duty` | за что отвечает, словами — чтобы через месяц не гадать |
| `scope` | зоны системы: `["radar","blast","memory","queue"]` |
| `join_limit_day` | сколько чатов в сутки этому аккаунту разрешено занимать очередью |
| `read_limit_day` | сколько чатов в сутки читать/опрашивать |
| `msg_limit_day` | потолок исходящих (соблюдают рассылки; `0` = не пишет) |
| `pause_min_sec` / `pause_max_sec` | пауза между действиями очереди |

Сессии и статусы живут в `accounts.json` (их пишет авторизация), ответственность и
лимиты — здесь. `db_sync` подтягивает первое во второе и **не затирает** `duty`,
`scope` и лимиты.

Текущее распределение — в `10 — Claude/Рабочее пространство/personal-os/Ферма Telegram-аккаунтов.md`.

## 5. Очередь: заходить постепенно

Смысл очереди: список интересных чатов можно составить сразу, а **заходить в них
сразу нельзя** — сотня заходов за час выглядит как бот и стоит аккаунта. Очередь
держит список и выдаёт его по нескольку штук в день, с паузами и лимитом на аккаунт.

```bash
node $D queue_add '{"items":[
  {"target":"@chat1","action":"info","reason":"кандидат в blast-список","priority":2},
  {"target":"@chat2","action":"read","reason":"посмотреть живость"},
  {"target":"https://t.me/+abc123","action":"join","account":"acc2"}
]}'

node $D queue_list '{"status":"pending"}'
node $D queue_run  '{"account":"acc2","limit":5,"dry":true}'   # что возьмёт и сколько бюджета
node $D queue_run  '{"account":"acc2","limit":5}'              # заход по-настоящему
node $D queue_set  '{"id":12,"status":"skipped","reason":"мёртвый чат"}'
```

| `action` | Что делает | Риск |
|----------|-----------|------|
| `info` | карточка чата: описание, участники (без вступления) | низкий |
| `read` | карточка + кэш последних сообщений (публичное читается без вступления) | низкий |
| `join` | вступить в чат, потом прочитать | считается по `join_limit_day` |

Поля записи: `target` (обязательно — `@юзернейм`, id или ссылка-приглашение),
`action`, `account` (кому поручено; пусто — возьмёт тот, кого запустили),
`priority` (1 вперёд всех), `reason`, `not_before` (не раньше даты).

Как ведёт себя `queue_run`:

- берёт только то, что влезает в остаток суточного бюджета аккаунта;
- пауза между чатами — случайная из `pause_min_sec`…`pause_max_sec` (по умолчанию 45–120 с),
  переопределяется `"pause":[5,10]`;
- аккаунт в статусе `cooldown` / `limited` / `banned` очередь не трогает вообще;
- **`FLOOD_WAIT` / `PEER_FLOOD` → полная остановка прохода**: запись возвращается в
  очередь с `not_before` на время ожидания, аккаунт уходит в `cooldown` (и в базе,
  и в `accounts.json`). Причина в темпе, а не в конкретном чате — следующий чат
  даст ровно то же самое;
- обычная ошибка (чата нет, приватный) — запись `failed`, проход продолжается.

Пометить чат сразу при добавлении в очередь нельзя — сначала заход, потом `db_tag`.

## 6. Ритм

| Что | Как часто | Кто делает |
|-----|-----------|-----------|
| `db_sync` (свежие диалоги) | каждый день в 9:20 | крон, задача `tg-chats-sync` |
| `db_sync` с `limit: 5000` | по воскресеньям | она же (полный проход зашит в скрипт) |
| `queue_run` | дважды в день, 13:10 и 21:10, по 2 чата | крон, задача `tg-queue-run` |
| `queue_run` для другого аккаунта | по необходимости | руками/агентом |
| `db_cache` для важного чата | по необходимости | руками/агентом |

Крон-задача зовёт `scripts/daily-sync.sh` — он глушит логи gramjs (иначе они утопят
отчёт: крон пишет в лог и stdout, и stderr) и печатает одну строку сводки:

```
база чатов: 2203 чатов, 20 сообщений в кэше · main: 500 · acc2: 227 · acc3: 25
```

Ошибка любого аккаунта роняет задачу — сбой всплывёт в «крон с ошибкой» на старте сессии.
Обычный проход берёт только свежие диалоги (`getDialogs` отдаёт их по убыванию
активности), поэтому чат, в котором что-то произошло, обновится в любом случае;
полный воскресный нужен, чтобы заметить покинутые и удалённые.

```bash
cd services/cron
python3 cronctl.py run tg-chats-sync      # прогнать сейчас
python3 cronctl.py disable tg-chats-sync  # выключить
bash ~/.claude/skills/telegram/scripts/daily-sync.sh 5000   # руками, глубоко
```

Заходы по очереди раскиданы на два прохода в день (задача `tg-queue-run`,
`scripts/queue-run.sh <аккаунт> <сколько за проход>`): 13:10 и 21:10, по 2 чата.
Дневной потолок держит не крон, а `join_limit_day` аккаунта — если проход упёрся
в лимит, он просто ничего не возьмёт и напишет об этом. Два коротких прохода
вместо одного длинного растягивают заходы по суткам: серия подряд — самый явный
признак бота.

```bash
bash ~/.claude/skills/telegram/scripts/queue-run.sh acc7 2   # проход руками
python3 cronctl.py disable tg-queue-run                      # выключить заходы
```

**`INVITE_REQUEST_SENT` — это не ошибка**, а чат с одобрением заявок: запрос ушёл
админам, вступление произойдёт (или нет) без нас. Проход помечает такую запись
как неудачную; её надо перевести в `done` руками — повторный заход только
продублирует заявку.

Точечно обновить кэш известного чата, не трогая очередь:

```bash
node $D db_cache '{"chat_id":"@durov","limit":100,"account":"acc2"}'
```

## 7. Грабли

- **`node:sqlite` до Node 23.4 живёт под флагом.** Драйвер перезапускает себя с
  `--experimental-sqlite` сам — снаружи вход один, `node driver.cjs <tool>`. Если
  Node обновится и флаг станет не нужен, перезапуск просто перестанет срабатывать
  (проверка `chatsdb.available()`).
- **База в WAL** — рядом с `chats.db` лежат `-wal` и `-shm`, это нормально. Копировать
  базу — только все три файла или через `sqlite3 .backup`.
- **`chats.db` наружу не отдаётся**: в ней названия личных чатов и кэш переписки.
  В `.gitignore`, как и `accounts.json`.
- **`getEntity` отдаёт голый id, `getDialogs` — размеченный.** Вся запись в базу идёт
  через `peerId()`; если добавляешь новый путь наполнения — тоже через него, иначе
  чат задвоится.
- **`db_chats` не знает того, чего не синкали.** Пустой ответ на заведомо существующий
  чат = не «чата нет», а «его нет у нас»: прогони `db_sync` или добавь в очередь.
- **Число участников и описание устаревают.** `db_sync` их не обновляет (в диалогах
  их нет) — свежие приходят только заходом (`info`/`read`).
- Запись `queue` уникальна по паре `target` + `action`: повторный `queue_add` того же
  чата не плодит дублей, а обновляет причину и приоритет.
