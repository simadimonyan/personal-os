# Ферма Telegram-аккаунтов

Как в Personal OS устроена работа с несколькими Telegram-аккаунтами: где лежат сессии,
как подключить аккаунт, как раздать роли, как не потерять аккаунт из-за лимитов.

---

## 1. Что такое ферма здесь

Ферма — это набор личных аккаунтов Димитри, подключённых к одному приложению Telegram
(`API_ID`/`API_HASH` общие), между которыми **распределена нагрузка и риск**:

- один аккаунт — основной, живой, с контактами и перепиской (терять нельзя);
- остальные — рабочие: рассылки, вступление в чаты, сбор данных, разведка публичных каналов;
- любой аккаунт можно поставить на паузу, не трогая остальные.

Смысл именно в разделении: если рабочий аккаунт словил лимит или блокировку, основной
цел, и вся система (память, экспорты, ассистент) продолжает работать.

Все аккаунты — **свои**, подтверждённые своими номерами. Ферма не про массовое создание
одноразовых аккаунтов и не про обход ограничений Telegram — такой сценарий тут не
поддерживается сознательно (см. §7).

## 2. Где что лежит

```
~/.claude/skills/telegram/
  .env             API_ID / API_HASH — общие на все аккаунты (+ legacy TELEGRAM_SESSION)
  accounts.json    сессии всех аккаунтов + метаданные фермы (chmod 600, в git не попадает)
  accounts.cjs     стор аккаунтов: чтение/запись, выбор сессии, метаданные
  auth.cjs         интерактивная авторизация и управление фермой
  auth-relay.cjs   авторизация шагами (для агента): состояние в .auth-pending.json
  farm.cjs         проверка живости сессий (общая для auth.cjs и driver.cjs)
  chats.db         база чатов всей фермы + очередь заходов (в git не попадает)
  chatsdb.cjs      схема и запросы базы
  chatsync.cjs     наполнение базы из Telegram и обработка очереди
  driver.cjs       все инструменты; поле "account" выбирает, от кого работать
```

Ответственность аккаунтов (`role`, `duty`, `scope`, суточные лимиты) живёт в базе
(таблица `accounts`), а не здесь: `accounts.json` держит только сессии и статусы.
Подробности — `references/chats-db.md`.

Запись в `accounts.json`:

```json
{
  "default": "main",
  "accounts": {
    "main": {
      "phone": "+7…", "session": "1Ap…", "username": "…", "id": "…", "addedAt": "…",
      "role": "личный", "note": "для чего аккаунт", "tags": ["ru"],
      "status": "active", "lastCheck": "…", "lastError": null
    }
  }
}
```

`session` — это ключ доступа к аккаунту. Файл под `chmod 600`, наружу (git, экспорт,
скриншот) не отдавать никогда.

## 3. Подключить аккаунт

Код подтверждения приходит в приложение Telegram — **ввести его может только Димитри**.
Агент запускает авторизацию сам только если сидит в интерактивном терминале; в Claude Code
пользователь запускает через префикс `!`.

```bash
! node ~/.claude/skills/telegram/auth.cjs add <label>
```

Спросит: номер (с `+`) → код из Telegram → пароль 2FA (если включён).
Метка (`label`) — короткое имя, по которому аккаунт вызывается: `main`, `blast`, `scout`, `reserve`.

Порядок при подключении пачки: по одному, между аккаунтами пауза 1–2 минуты.
Несколько подряд логинов с одного IP Telegram воспринимает нервно.

**Пачкой** — скрипт проводит по списку меток, с паузой между аккаунтами и отчётом в конце:

```bash
! bash ~/.claude/skills/telegram/scripts/add-farm.sh acc4 acc5 acc6
! bash ~/.claude/skills/telegram/scripts/add-farm.sh          # метки спросит по ходу
! FARM_PAUSE=0 bash ~/.claude/skills/telegram/scripts/add-farm.sh acc4 acc5   # без пауз
```

Упавший аккаунт (не тот код, нет доступа к номеру) не роняет проход — скрипт идёт дальше,
а в итоговом списке видно, кто не подключился. Больше 5–6 аккаунтов за раз лучше не гнать:
серия новых сессий с одного IP — сама по себе повод для проверки.

**Руками агента** (`auth-relay.cjs`) — когда терминал не интерактивный: вход разнесён на
шаги, между шагами состояние лежит на диске (`.auth-pending.json`, chmod 600), так что код
и пароль присылает Димитри в чат, а команды выполняет агент.

```bash
node ~/.claude/skills/telegram/auth-relay.cjs start acc11 +79991234567   # запросить код
node ~/.claude/skills/telegram/auth-relay.cjs code acc11 12345           # ввести код
node ~/.claude/skills/telegram/auth-relay.cjs password acc11 '<пароль>'  # 2FA, если попросили
node ~/.claude/skills/telegram/auth-relay.cjs status                     # что не доведено
node ~/.claude/skills/telegram/auth-relay.cjs cancel acc11               # бросить вход
```

Недоведённый вход переживает конец сессии — вернуться к нему можно через часы, `status`
покажет, кто на каком шаге стоит. Успешный вход сам пишет аккаунт в ферму со `status: active`.

Пароль 2FA — это **облачный пароль Telegram** (тот, что просят при входе на новом
устройстве), не пароль от почты и не код из сообщения.

Остальные команды:

```bash
node ~/.claude/skills/telegram/auth.cjs list                    # ферма целиком
node ~/.claude/skills/telegram/auth.cjs check [label]           # живы ли сессии
node ~/.claude/skills/telegram/auth.cjs set <label> role рассылки
node ~/.claude/skills/telegram/auth.cjs set <label> note "интро по фриланс-чатам"
node ~/.claude/skills/telegram/auth.cjs set <label> tags "blast, ru"
node ~/.claude/skills/telegram/auth.cjs set <label> status cooldown
node ~/.claude/skills/telegram/auth.cjs default <label>         # сменить основной
node ~/.claude/skills/telegram/auth.cjs remove <label>          # выкинуть из фермы
node ~/.claude/skills/telegram/auth.cjs import-legacy <label>   # забрать сессию из .env
```

**Общая группа фермы.** Все аккаунты сидят в служебной группе `Farm` (`-1002263449848`,
`main` — админ): в одном месте видно, кто жив, и есть куда написать между аккаунтами, не
заводя переписок один-на-один. Сверить состав и добрать отставших:

```bash
node ~/.claude/skills/telegram/driver.cjs group_members '{"chat_id":"-1002263449848"}'
node ~/.claude/skills/telegram/driver.cjs add_member '{"chat_id":"-1002263449848","user":"acc11"}'
```

`group_members` подписывает участников метками фермы, `add_member` идемпотентен и для своих
умеет обход через ссылку-приглашение (см. §8).

`remove` удаляет сессию из стора, но **не разлогинивает** аккаунт на стороне Telegram —
чтобы оборвать доступ по-настоящему, надо снять сессию в приложении
(Настройки → Устройства).

## 4. Работать от конкретного аккаунта

Поле `account` в JSON-аргументах любого инструмента:

```bash
node ~/.claude/skills/telegram/driver.cjs get_me       '{"account":"blast"}'
node ~/.claude/skills/telegram/driver.cjs get_dialogs  '{"account":"scout","limit":50}'
node ~/.claude/skills/telegram/driver.cjs send_message '{"account":"blast","chat_id":"@chat","text":"…"}'
```

Приоритет выбора: `account` в аргументах → env `TELEGRAM_ACCOUNT` → `default` из стора →
legacy-сессия из `.env`.

Env удобен, когда чужой скрипт про ферму не знает:

```bash
TELEGRAM_ACCOUNT=scout python3 services/radar/collectors.py
```

Инструменты фермы в драйвере (клиент не поднимают, кроме `check_accounts`):

```bash
node ~/.claude/skills/telegram/driver.cjs list_accounts
node ~/.claude/skills/telegram/driver.cjs check_accounts '{"accounts":["blast","scout"]}'
```

## 5. Роли: кто за что отвечает

Роль — это договорённость, а не техническое ограничение. Она пишется в `role`/`note`,
чтобы через месяц не гадать, зачем аккаунт.

| Роль | Что делает | Чего не делает |
|------|-----------|----------------|
| `личный` | переписка, экспорты для памяти, ассистент, публикации в свой блог | не рассылает, не вступает в десятки чатов |
| `рассылки` | интро по фриланс- и job-чатам (`tg-freelance-blast`), холодные сообщения | не хранит личную переписку |
| `чтение` | сбор публичных каналов (радар, источники, разведка конкурентов) | не пишет сообщений вообще |
| `резерв` | подключён, прогрет, лежит на случай потери рабочего | не используется в потоке |

Кто из системы каким аккаунтом ходит сейчас — в заметке
`10 — Claude/Рабочее пространство/personal-os/Ферма Telegram-аккаунтов.md`.
По умолчанию все потребители (радар, экспорты памяти, ассистент, blast) берут `default`,
пока им явно не передали `account`.

## 6. Статусы и проверка живости

`status` в сторе:

| Статус | Значение |
|--------|----------|
| `active` | рабочий, можно давать нагрузку |
| `cooldown` | отдыхает после интенсива или после флуд-лимита; не трогать |
| `limited` | Telegram ограничил (спам-блок, `PEER_FLOOD`) — только чтение, писать нельзя |
| `banned` | потерян |
| `unknown` | не проверялся или проверка упала |

```bash
node ~/.claude/skills/telegram/auth.cjs check          # все аккаунты
node ~/.claude/skills/telegram/auth.cjs check blast    # один
```

Проверка делает `getMe` каждой сессией и обновляет `status`/`lastCheck`/`lastError`.
Ручные пометки (`cooldown`, `limited`, `banned`) успешная проверка не стирает — их
снимает только человек командой `set … status active`.

Разумный ритм — раз в сутки или перед крупной рассылкой. Гонять чаще нет смысла.

## 7. Правила, чтобы не потерять аккаунты

Всё это — не паранойя, а причины, по которым аккаунты реально уходят в спам-блок:

1. **Личный аккаунт не рассылает.** Массовые сообщения — только с рабочего.
2. **Паузы между сообщениями** — 30–90 секунд, случайные, как в `tg-freelance-blast`.
   Ровный интервал виден в статистике лучше, чем большая частота.
3. **Дневной потолок** — десятки, а не сотни сообщений незнакомым. Новый аккаунт —
   первые дни единицы.
4. **Свежий аккаунт греется:** аватар, имя, пара дней обычной жизни (читает, состоит
   в чатах), и только потом любая исходящая активность. Аккаунт, зарегистрированный
   час назад и сразу начавший писать, блокируется почти гарантированно.
5. **Одна личность = один номер.** Ферма из своих номеров; покупные и виртуальные номера
   не заводим — их отбирают вместе с аккаунтом.
6. **Первым словом на `PEER_FLOOD` / `FLOOD_WAIT`** — остановиться и поставить `cooldown`,
   а не переключаться на следующий аккаунт и продолжать то же самое. Причина в поведении,
   а не в аккаунте.
7. **Жалобы важнее лимитов.** Сообщение, на которое жмут «спам», стоит дороже сотни
   сообщений, которые просто игнорируют: пишем по адресу и по делу.
8. **Границы.** Ферма — для своих аккаунтов и своих задач: отклики, работа с
   сообществами, сбор публичных данных, память. Массовая регистрация, накрутка,
   обход блокировок, чужие аккаунты — вне системы; такие просьбы не выполняются,
   и предупреждение о риске даётся до действия, а не после.

Хук `risk_screen.py` в проекте подсвечивает запросы, где такое можно словить —
он предупреждает, а не запрещает.

## 8. Грабли

- `AUTH_KEY_UNREGISTERED` / `SESSION_REVOKED` — сессия умерла (разлогинили в приложении
  или Telegram сбросил). Лечение: `auth.cjs add <label>` тем же ярлыком.
- `FLOOD_WAIT_X` — подождать X секунд, не ретраить сразу. Часто прилетает и на чтении,
  если гонять `search_public` без пауз (~1 с между запросами).
- Проверка `check` не отличает бан от разлогина — обе выглядят как мёртвая сессия.
  Настоящее состояние видно, если войти номером с телефона.
- `accounts.json` пишется целиком: два параллельных процесса, меняющих ферму, могут
  затереть правки друг друга. Авторизацию и `set` делать по одному.
- Смена `default` меняет поведение всей системы разом (радар, экспорты, ассистент,
  blast берут default) — менять осознанно.
- `remove` не разлогинивает (см. §3).
- Логи gramjs идут в stderr, JSON — в stdout. Если парсер получил огрызок, дело не в
  логах, а в чём-то другом (см. память `telegram-driver-stdout-interleave`).
- `PHONE_CODE_INVALID` / `PASSWORD_HASH_INVALID` не съедают вход: состояние держится, можно
  пробовать дальше. Но подряд неверные попытки Telegram притормаживает `FLOOD_WAIT`, поэтому
  вслепую перебирать нельзя — лучше свериться. Код перезапрашивается через
  `cancel` + `start` (свежий код, новый `phoneCodeHash`).
- Прежде чем верить `PASSWORD_HASH_INVALID` на пароле, который точно верный, — проверить,
  что в Telegram уходит именно пароль. У `auth-relay.cjs password` разбор аргументов брал
  срез с `argv[3]` и приклеивал к паролю метку аккаунта (`"acc9 пароль"`); внешне это
  выглядело как неверный пароль. Починено 2026-08-11 (`slice(4)`).
- Аккаунт фермы не может пригласить другой аккаунт фермы по id: `getInputEntity` отдаёт
  «Could not find the input entity» — приглашаемого нет в кэше сущностей приглашающего
  (та же грабля, что у `getEntity` по голому id, см. память `telegram-entity-needs-dialogs`).
  Обход зашит в `add_member`: сначала пробуем `@username`, потом id, потом админ выпускает
  ссылку-приглашение и приглашаемый входит по ней своей сессией.
- Новый аккаунт попадает в `chats.db` (роли, лимиты, `db_account_set`) только через
  `syncAccounts` — а его тянет `db_sync`. Чтобы завести аккаунт в базу, не ходя в Telegram:
  `node --experimental-sqlite -e "const d=require('./chatsdb.cjs'),s=require('./accounts.cjs');d.syncAccounts(d.open(),s)"`.
